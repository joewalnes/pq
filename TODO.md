## Bugs

- [x] P1: `pq sql` silently drops duplicate-named columns — Fixed for single-file tables. Located by instrumentation, not inspection: a probe printing the schema at each hop showed the file has `["id","id"]` but the `TableProvider` built by `SessionContext::register_parquet` already has `["id"]`, so the loss is at *registration*, upstream of planning and of every writer. Cause is `ParquetFormat::infer_schema` → `Schema::try_merge` (datafusion 44.0.0), whose `SchemaBuilder::try_merge` matches fields by name (arrow-schema 53). `DFSchema` is not involved — it holds duplicates fine. `pq cat --where` was affected identically (also `query_with_where` → DataFusion) and is fixed too. `pq-query` now detects duplicate top-level names and registers the file under unique ones (`id`, `id_1`, ...), announcing the rename on stderr; the rename is deliberately visible and not reversed, because a result set whose names can't be typed back into a query is the trap that made the second column unreachable, and the mapping isn't reversible when a file legitimately contains both `id` and `id_1`. Rejected on evidence: supplying a pre-renamed schema via `ParquetReadOptions::schema` — the reader still matches by name and substitutes NULLs for the renamed column. Guards: `crates/pq-cli/tests/sql_duplicate_columns_tests.rs` (13 tests) and the rewritten `sql_preserves_duplicate_columns_through_every_output_path` in `csv_correctness_tests.rs`.
- [x] P3: duplicate-named columns were still collapsed for *directory* tables — Fixed by **refusing**, not repairing. `SELECT * FROM 'somedir.parquet'` (and `pq cat --where` on a directory) now errors, exit 1, naming the offending file, when any file DataFusion would read for that directory has duplicate top-level column names. Before: the directory route returned one column carrying the *second* column's data under the *first* column's name, exit 0, no note, while the same bytes queried as a file answered correctly. Refusal rather than repair because (a) a directory's files are merged *by name*, so a duplicate has no unambiguous counterpart in a sibling file and any rule would be a guess presented as data; (b) the only preserving mechanism pq has materializes the table, and a directory is precisely what does not fit in memory; (c) supplying a pre-disambiguated schema to `ListingTable` fails the same way it failed for single files (the reader matches by name and substitutes NULLs). pyarrow refuses the same input (`ArrowInvalid: Can't unify schema with duplicate field names`). The file set checked comes from DataFusion's own `ListingTableUrl::list_all_files`, not a hand-rolled walk: measured, DataFusion reads `top.parquet` and `k=1/hive.parquet` but not `nested/deep.parquet`, so a recursive walk over-refuses and a flat one under-refuses — both mistakes have a guard in `sql_duplicate_columns_tests.rs`, each verified by writing the wrong walk and watching the test fail. Cost: one footer read per file per directory registration (metadata only, same order as `ListingTable`'s own schema inference).

- [ ] P3: duplicate-named columns on *remote* tables are unverified, and a scanned duplicate-named file is still fully materialized — (1) The `s3://`/`https://` branch gets the single-file check via `pq_core::async_reader::read_arrow_schema`, but that could not be exercised: `make test-integration` needs Docker and was guard-blocked. It also costs one extra footer read per remote table, since pq's metadata cache is not DataFusion's. A remote *prefix* (a directory-shaped `s3://bucket/dir/`) is not covered by the local directory refusal and is untested — `read_arrow_schema` would most likely error on it. (2) A duplicate-named file that is actually scanned is read via `MemTable`, so it is fully materialized and loses predicate/projection pushdown — including for `LIMIT 1` (measured 318 MB RSS vs 28 MB for a unique-named twin). Accepted as loud-over-silent. Registration itself is now lazy, so a path that appears only as a string literal is no longer read.

- [ ] P2: nested duplicate field names inside a struct are collapsed on output — Pre-existing and unrelated to DataFusion: `pq_query::convert::batch_to_json_rows` builds each row as a JSON object keyed by field name, so a struct containing two fields with the same name loses all but the last. Reproduced on a file whose one column `s` is `struct<x:int64, x:int64>` holding `[1,2]` and `[10,20]`: both `pq cat -f jsonl` and `pq sql "SELECT * FROM ..." -f jsonl` print `{"s":{"x":10}}` / `{"s":{"x":20}}`, exit 0 — identical output from the two commands, which is what rules DataFusion out. (pyarrow declines the same conversion: `ValueError: Converting to Python dictionary is not supported when duplicate field names are present`.) Affects every JSON/JSONL output path. Found during the duplicate-column work and deliberately left out of scope there — the top-level fix operates on the table schema at registration, which cannot see inside a struct. A fix has to decide what a JSON object with duplicate keys should even be (rename like the top-level fix does, or emit an array), so it needs its own design.
- [ ] P3: a `pq sql` query that names the same file twice always fails — `register_files_from_query` walks the query's quoted strings and registers each occurrence, without deduplicating, so a self-join fails at registration: `pq sql "SELECT x.a FROM 'f.parquet' x JOIN 'f.parquet' y ON x.a = y.a"` gives `Execution error: The table f.parquet already exists`, exit 1. Pre-existing and not specific to duplicate columns — confirmed on a pre-fix binary against both a unique-named and a duplicate-named file. Found while adversarially probing the duplicate-column work and left alone deliberately: the fix (dedupe the collected paths) is three lines but touches the registration loop that two bugs have already been fixed in this week, so it wants its own change and its own guard.
- [ ] P2: error messages print the same sentence twice — `pq-core`'s error type's `Display` includes its own source chain, which `anyhow` then appends again, so several commands emit `Error: IO error: <msg>: <msg>`. Reproduce: `pq import x.jsonl -o /dev/stdout > out.bin`. The fix is in the `pq-core` error type, changes error text for *every* command, and rewrites four golden expectations — deliberately refused as a drive-by inside an unrelated CSV commit, so it needs its own change with the expectation edits reasoned through (never regenerated).
- [x] TUI: row number unreadable on selected row — Fixed: row number now uses `fg(White)` on selected row, `fg(DarkGray)` otherwise.
- [ ] P2: Interactive viewer demo GIF missing from docs site — The homepage and viewer page reference `img/tui-viewer.gif` but the GIF has never been committed. `make demos` generates it via `demos/tui-viewer.py` + asciinema + agg, but the docs CI workflow doesn't run this step. Either generate and commit the GIF, or add asciinema/agg to the docs workflow.
- [ ] P2: `jq -o` and `cat -O` ignore `-f`/`--format` and silently pick the format from the output file's extension — unlike `sql -o`/`export -o`, which honor an explicit `-f` (with a stderr note) and hard-error on an unrecognized extension with no `-f`. Repro: `pq jq src.parquet '.' -o out.csv -f json` writes CSV, `-f` silently ignored. Both also bypass `crates/pq-transform/src/output_guard.rs::with_atomic_output` entirely (they write straight to the destination via `write_output.rs`'s `File::create`), contradicting that module's own doc comment that every `-o`-writing command goes through it. Fixing this needs `write_output.rs::write_batches_to_file`/`json_values_to_file` to accept an explicit format + announce overrides (mirroring `sql.rs`'s `resolve_output_format`) and to route through `with_atomic_output` — out of scope for whoever owns `write_output.rs`/`output_guard.rs` at the time this was filed.
