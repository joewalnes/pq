## Tier 1 — High impact

- [ ] `diff <a> <b>` — Compare two parquet files: schema diff (added/removed/changed columns, type changes) and optional data diff (row-level, sampled or full)
- [ ] `repack <file>` — Rewrite with different compression (`--compression zstd|snappy|gzip|none`), row group size (`--row-group-size`), encoding, or sort order
- [ ] `sort <file>` — Sort by one or more columns (`--by col1,col2 --desc`) and write new file; could also be a flag on `repack`
- [x] `export <file>` — Parquet to CSV/JSON/JSONL file output (`-o output.csv`); format auto-detected from extension
- [x] Remote file access — S3 and HTTPS supported for all read-only commands via `object_store` + `ParquetObjectReader`. Only footer + requested row groups are fetched. Transform commands remain local-only.
- [x] Remote file access: GCS (`gs://`) and Azure (`az://`, `abfss://`) — wired via `gcp`/`azure` features on `object_store`; credentials read from environment

## Bugs

- [x] P1: `pq cat`'s default table output (and `-f plain`) silently misaligned columns across multi-file input — Fixed. `render_table`/`render_plain` built the header from `batches[0].schema()` alone and zipped every later batch's values in positionally; combining files whose column names appear in a different order (or whose sets differ at all) swapped or dropped values under the wrong header, exit 0. `-f csv`/`-f jsonl` were already correct (csv had the identical bug, fixed earlier via a union header resolved by `(name, occurrence)`). Both renderers now reuse that exact alignment (`write_output::union_columns`/`column_indices`) instead of a third strategy. A column absent from a given file now renders as `·`, distinct from a genuine NULL (still blank). Duplicate-named columns unaffected. Guards: `crates/pq-cli/tests/table_alignment_tests.rs` (9 tests: reorder, disjoint, 3-file partial overlap, dup-name control, dup-name+plain-file combination, NULL-vs-missing distinction, single-file control, cross-format `table`/`csv`/`jsonl` agreement); all 7 non-control tests independently confirmed to fail against the pre-fix renderer.
- [ ] P2: `pq sql` error chains print THREE times, not two — `DataFusion error: SQL error: ParserError(...): SQL error: ParserError(...): sql parser error: ...`. The pq-core doubling was fixed separately; this one lives in `crates/pq-query`/`sql.rs`, where a DataFusion error is wrapped with context that already contains the source text. Reproduce: `pq sql "SELECT"`. Same class as the pq-core bug, different owner, and it survives that fix — verified after it landed.
- [ ] P3: `output_guard.rs` has a race in its `/dev/fd` handling under concurrent load — `pq import x.jsonl -o /dev/stdout > out.bin` fails roughly 1 run in 5 when the crate's tests run in parallel, and 0 in 9 when run in isolation. Found while building a guard for the error-doubling bug; the flaky repro was replaced with a deterministic equivalent rather than shipped. `can_stage` resolves `/dev/stdout` to `/dev/fd/1`, and when stdout is a regular file `metadata().is_file()` is true, so the guard tries to stage inside `/dev/fd`. Not diagnosed further.
- [x] P1: `pq sql` silently drops duplicate-named columns — Fixed for single-file tables. Located by instrumentation, not inspection: a probe printing the schema at each hop showed the file has `["id","id"]` but the `TableProvider` built by `SessionContext::register_parquet` already has `["id"]`, so the loss is at *registration*, upstream of planning and of every writer. Cause is `ParquetFormat::infer_schema` → `Schema::try_merge` (datafusion 44.0.0), whose `SchemaBuilder::try_merge` matches fields by name (arrow-schema 53). `DFSchema` is not involved — it holds duplicates fine. `pq cat --where` was affected identically (also `query_with_where` → DataFusion) and is fixed too. `pq-query` now detects duplicate top-level names and registers the file under unique ones (`id`, `id_1`, ...), announcing the rename on stderr; the rename is deliberately visible and not reversed, because a result set whose names can't be typed back into a query is the trap that made the second column unreachable, and the mapping isn't reversible when a file legitimately contains both `id` and `id_1`. Rejected on evidence: supplying a pre-renamed schema via `ParquetReadOptions::schema` — the reader still matches by name and substitutes NULLs for the renamed column. Guards: `crates/pq-cli/tests/sql_duplicate_columns_tests.rs` (13 tests) and the rewritten `sql_preserves_duplicate_columns_through_every_output_path` in `csv_correctness_tests.rs`.
- [ ] P3: duplicate-named columns are still collapsed for *directory* tables and remote files are unverified — Two gaps left by the fix above. (1) `SELECT * FROM 'somedir.parquet'` where the path is a directory goes straight to DataFusion's `ListingTable` (which merges schemas across files), so duplicates there are still silently collapsed. The duplicate check is skipped for non-regular-files deliberately: an earlier version applied it unconditionally and broke directory tables outright with "Is a directory (os error 21)" — guarded now by `a_directory_table_still_works`. (2) The `s3://`/`https://` branch does get the check, via `pq_core::async_reader::read_arrow_schema`, but that could not be exercised: `make test-integration` needs Docker and was guard-blocked. It also costs one extra footer read per remote table, since pq's metadata cache is not DataFusion's. (3) A duplicate-named file is read via `MemTable`, so it is fully materialized and loses predicate/projection pushdown — including for `LIMIT 1`.
- [x] P2: error messages print the same sentence twice — Fixed: six `PqError` variants (`FileOpen`, `ParquetRead`, and the `#[from]` variants `Parquet`, `Arrow`, `Io`, `Json`) both interpolated their `source`'s text into their own `Display` *and* implemented `source()`, so `anyhow`'s `{:#}` (`pq-cli/src/main.rs`) printed the cause once from the message and again from the chain walk. `Display` now renders only its own message; `source()` still carries the cause, so filenames and OS/Parquet/JSON detail all still reach the user, just once. Guards: `crates/pq-core/src/error.rs`'s unit tests (one hop, every doubling-prone variant) and `crates/pq-cli/tests/error_display_tests.rs` (end-to-end shape check across five real failing commands: missing file, zero-byte/corrupt parquet, malformed JSON import, `-o` naming an existing directory). Four golden expectations in `tests/golden/tests/error-handling.md` were hand-edited to drop the trailing repeat. Not fixed: `pq sql`'s own error chain (`DataFusion error: ... : ... : sql parser error: ...`, owned by `pq-query`/`sql.rs`, out of this change's file scope) still triples for a different reason and is unaffected by this fix. Also not used as an automated guard: the literal `import -o /dev/stdout` repro named when this bug was filed reaches the same `PqError::Io` doubling, but intermittently (~1 run in 5 under concurrent test load) takes a different path through an unrelated pre-existing race in `output_guard.rs`'s `/dev/fd` handling — kept as an `#[ignore]`d manual-repro test rather than shipped as a flaky gate.
