# TODO

## Tier 1 — High impact

- [x] Multi-file path support — All data commands now accept multiple files and glob patterns (e.g. `pq cat data/*.parquet`). Glob expansion via `files::resolve_files()`.
- [ ] `diff <a> <b>` — Compare two parquet files: schema diff (added/removed/changed columns, type changes) and optional data diff (row-level, sampled or full)
- [ ] `repack <file>` — Rewrite with different compression (`--compression zstd|snappy|gzip|none`), row group size (`--row-group-size`), encoding, or sort order
- [ ] `sort <file>` — Sort by one or more columns (`--by col1,col2 --desc`) and write new file; could also be a flag on `repack`
- [x] `export <file>` — Parquet to CSV/JSON/JSONL file output (`-o output.csv`); format auto-detected from extension
- [x] Remote file access — S3 and HTTPS supported for all read-only commands via `object_store` + `ParquetObjectReader`. Only footer + requested row groups are fetched. Transform commands remain local-only.
- [x] Remote file access: GCS (`gs://`) and Azure (`az://`, `abfss://`) — wired via `gcp`/`azure` features on `object_store`; credentials read from environment

## Tier 2 — Differentiation

- [x] `stats --describe <file>` — Statistical summary per column: count, nulls, null%, min, max, mean, stddev, distinct, top-K frequent values (shipped as a flag on `stats`, not a standalone `describe` command)
- [x] `grep <file> <pattern>` — Search across all columns for a regex match; supports `-i` case-insensitive, `--limit`, `-c` column filter
- [x] `split <file>` — Split by row count (`--rows`) or partition key (`--partition-by col`); Hive-style partitioned output
- [ ] `schema evolve <file>` — Add columns (`--add name:type`), drop (`--drop col`), rename (`--rename old:new`), cast types (`--cast col:type`)
- [x] `validate <file>` — Check file integrity: valid footer, row count consistency, column count per row group, statistics sanity, data readability

- [x] P2: `stats --describe` with `--sample-size` silently reports on the FIRST FILE ONLY — Fixed. Two files holding [1,2,3] and [100,200,300], `--sample-size 2` gave `count: 2, max: 2` drawn solely from the first file, exit 0, no indication the second was ignored — and because the second file was never opened, the cross-file schema-compatibility guard never saw it either, so a genuinely incompatible file could pass unnoticed the same way. Kept the existing multi-file rule from the `tail`/`sample` fix (concatenation in argument order, `--sample-size` a total row budget, not per-file) rather than inventing new semantics: a file the budget never reaches still contributes 0 rows, but it can no longer vanish. Guards: `crates/pq-cli/tests/describe_tests.rs` (8 new tests: sample size below/at/above the total, first-file-larger-than-sample, incompatible second file behind a saturated budget, zero-row file among non-empty ones, single-file control, plain-`stats` non-regression check), all 7 sample-size-related tests independently confirmed to fail against the pre-fix code (including the dangerous case: the incompatible-schema test got an unexpected exit 0 on the old binary). `crates/pq-cli/tests/cli_tests.rs::test_describe_json` updated for the new JSON envelope.
- [x] P1: `stats --describe a.parquet b.parquet` silently mislabelled data when files had different column names but matching types — Fixed. - [ ] P3: the atomic output guard breaks hardlinks and drops xattrs and ACLs — `fs::rename` replaces the directory entry, where the previous `File::create` wrote through the inode. - [x] P3: duplicate-named columns were still collapsed for *directory* tables — Fixed by **refusing**, not repairing. `SELECT * FROM 'somedir.parquet'` (and `pq cat --where` on a directory) now errors, exit 1, naming the offending file, when any file DataFusion would read for that directory has duplicate top-level column names. Before: the directory route returned one column carrying the *second* column's data under the *first* column's name, exit 0, no note, while the same bytes queried as a file answered correctly. Refusal rather than repair because (a) a directory's files are merged *by name*, so a duplicate has no unambiguous counterpart in a sibling file and any rule would be a guess presented as data; (b) the only preserving mechanism pq has materializes the table, and a directory is precisely what does not fit in memory; (c) supplying a pre-disambiguated schema to `ListingTable` fails the same way it failed for single files (the reader matches by name and substitutes NULLs). pyarrow refuses the same input (`ArrowInvalid: Can't unify schema with duplicate field names`). Cost: one footer read per file per directory registration (metadata only, same order as `ListingTable`'s own schema inference).
